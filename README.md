# 北林 CS2 Major 报名系统 · 项目总结

北京林业大学 CS2（Counter-Strike 2）校赛报名小程序 —— 微信小程序（原生）+ FastAPI 全栈项目。

> 一个功能完整的电竞校赛报名平台：注册登录、队伍组建、赛事报名、自动编排、比分录入、时间协商、段位体系、在校认证、AI 审核、管理后台。**已上线**（真实微信登录 + 小程序发布 + Docker 部署于 bjfumajor.com）。项目经历了一次完整的安全审查与修复（27 个问题，25 项已闭环），以下是内容、经验与教训的完整总结。

## 📦 项目内容

### 用户端

- **微信登录**：JWT 令牌认证，已接入真实微信登录（`wx.login` code → jscode2session 换 openid），保留 mock 开关供本地开发
- **段位体系**：D 段、C/B/A 各三小段（基础、+、++）及 S 段 50 星（金 S / 钻 S / 魔王 S），水平分与段位自动挂钩
- **段位认证必审（防炸鱼）**：报名与入队均强制上传完美/5E 段位截图，AI 识别段位；前端报名拦截 + 后端接口二次校验 + 「报名后入队自动补报名」路径同步拦截
- **在校认证**：上传学信网/校园卡截图 → AI 预审（置信度 ≥0.9 自动通过/驳回，否则转人工）→ 管理员复核兜底
- **队伍系统**：创建队伍（自动成为队长）、申请入队、队长审核、邀请/按学号拉人、退队/踢人/解散、人才市场（已报名未组队的自由人）、队长自定义队伍 Logo
- **赛事系统**：赛事浏览、队伍/个人报名（个人报名只需学籍+段位两个认证，无需管理员审核）、报名审核、状态管理
- **赛程编排**：按队伍水平分分配种子 → 蛇形分组 → 双循环/单循环小组赛 → 附加赛（三组赛制；四组跳过）→ 传奇组上下区 → 6 强淘汰赛，全自动生成
- **比分系统**：小组赛单局比分 / 淘汰赛 BO3 三局小分录入，小局弹层查看
- **时间协商**：管理员为各阶段设限定时段 → 双方队长在窗口内提交比赛时间 → 对方同意生效 / 拒绝作废（带 expected_time 防竞态）
- **界面（浅色主题）**：白 + 天蓝青设计令牌；左侧抽屉导航；功能拆分为独立页面（赛事/我的队伍/所有队伍/消息/认证/设置/个人资料）

### 管理端（admin / reviewer）

- 用户管理：搜索、设学号、设段位（自动同步水平分）、权限分配
- 队伍审核、赛事管理、**报名审核（按队伍批量通过）**
- 认证审核：待认证列表、截图预览、AI 预审置信度展示、通过/驳回
- 段位申请审批：AI 识别段位更新申请，管理员通过（可覆盖 AI 结果）/驳回
- 时间窗口管理：为各阶段（小组赛/附加赛/传奇组上下区/淘汰赛）设置限定时段
- 赛程一键编排（种子/分组/对阵/晋级推进）+ 对阵 CSV 导出

## 🗄 数据库设计（11 张表）

| 表 | 说明 |
|----|------|
| `users` | 用户：微信标识、学号、认证状态、角色、段位、水平分、头像、个人介绍 |
| `rank_applications` | 段位更新申请：用户再次上传段位截图后，提交管理员审批 |
| `teams` | 队伍：队名(唯一)、队长、审核状态、水平分、Logo |
| `team_members` | 队伍成员：队伍/用户、队内角色（一人一队唯一约束） |
| `team_applications` | 入队申请：用户申请、队长审核 |
| `team_invitations` | 入队邀请：队长邀请、用户同意 |
| `matches` | 赛事：名称、队伍上限、人数、类型（新生赛/大赛）、报名时间窗、状态 |
| `match_rounds` | 对阵：轮次、双方队伍、比分、胜者、BO3 小分、比赛时间与双方确认状态 |
| `team_progress` | 队伍赛事进度：阶段（挑战者/传奇/淘汰）、种子、分组 |
| `registrations` | 报名：队伍/个人报名、审核状态（(match_id, user_id) 唯一约束） |
| `stage_windows` | 阶段时间窗口：管理员为各阶段设置的限定时段 |

**关键业务规则**：

- **个人报名** = 学籍认证 + 段位认证两个判断，直接通过，无需管理员审核；
- **队伍报名** = 全员学籍 + 段位 + 人数上限 + （新生赛）≥3 名新生，报名后由管理员审核；
- **入队**（拉人/申请/邀请）= 若队伍已报名赛事，新成员必须学籍 + 段位双认证，并自动补报名、受队伍人数上限约束；
- **退队/被踢** = 随队报名恢复为个人报名（认证齐全则直接通过）。

## ✨ 技术亮点

- **前后端分离**：RESTful API + Pydantic 全量校验，前后端只靠 URL 路径握手
- **防炸鱼设计**：段位认证设为报名硬门槛，且堵住「报名后拉人入队」绕过路径（三段拦截）
- **AI 视觉审核**：智谱 GLM-5V-Turbo 双场景（学信网/校园卡真伪 + 完美/5E 段位识别），置信度分级：≥0.9 自动处理，否则转人工，AI 失败不影响主流程
- **完整赛制编排**：种子 → 蛇形分组 → 循环赛 → 传奇组 → 淘汰赛 BO3 全自动，可幂等重试
- **时间协商**：阶段时间窗口 + 双方确认 + expected_time 乐观锁防并发覆盖
- **上传安全**：魔数校验（不信 content-type）+ 大小限制 + 随机文件名，统一收敛到 `upload_service`
- **并发防护**：唯一约束 + `SELECT ... FOR UPDATE` 行锁 + IntegrityError 兜底转 400
- **数据库双轨**：SQLite 开发 / MySQL 生产可切换，全字段中文注释

## 💡 开发经验（踩坑记录）

### 数据库

1. **`create_all` 只建新表，不补列/不补约束**。项目先后三次加字段/约束（`match_rounds` 时间确认字段、`teams.logo`、`registrations` 唯一约束），每次都需手写 ALTER SQL 并本地+生产各执行一次。教训：**任何 schema 变更都要附带迁移 SQL**，不能依赖启动时自动建表。
2. **SQLite 默认不强制外键，MySQL InnoDB 强制**。删赛事漏删 `StageWindow`、解散队伍漏删 `MatchRound` 这类 bug 在 SQLite 开发期完全无感，上线 MySQL 后直接外键错误 500。教训：**本地 SQLite 跑通 ≠ 生产 MySQL 没问题**，删除链路的完整性要按生产语义逐条核对。
3. **枚举存数据库**：SQLAlchemy `SAEnum` 序列化出来是大写名，前端统一用 `normalizeRole` 递归转小写，避免各页面重复判断。

### 后端（FastAPI / 业务）

4. **路由顺序**：`/{team_id}` 这类动态路由会拦截固定路径（`/join`、`/talent-market`、`/assign` 都踩过 422），固定路径必须注册在动态路由之前。
5. **鉴权分层**：不要写「上帝鉴权函数」，而是抽**原子守卫**（`get_current_user` 登录、`require_admin` 管理端、`require_admin_only` 仅超管、`_require_captain` 队长、`_ensure_can_join` 入队资格、`_ensure_member_limit` 人数上限），在接口里显式组合。业务判断留在调用点，通用判断才进公共函数。
6. **业务闭环要全局看**：入队会触发「自动补报名」，所以入队入口必须和报名入口做**同样的认证校验**——只改报名校验、不改入队校验，就会产生「先报名后拉人绕过段位认证」的漏洞。任何一个会联动其它表的动作，都要排查所有能走到它的路径。
7. **个人报名规则极简**：只需学籍 + 段位两个判断、直接通过，不设多余审核环节；队伍报名才需要管理员审核。
8. **并发一致性**：先查再插的判重都是 TOCTOU 漏洞。正确姿势 = 数据库唯一约束兜底 + `IntegrityError` 捕获转 400 + 关键操作 `SELECT ... FOR UPDATE` 串行化。
9. **幂等设计**：管理端「生成对阵」「传奇组分区」这类按钮重复点击会重复造数据，必须在服务层加幂等保护（已存在则拒绝）。
10. **健壮性**：外部输入（JSON 小分、group_names 数组）解析要 try/except 转 400，除零要防御，负比分要拒绝——**任何 500 都是可以避免的**。

### 上传与安全

11. **content-type 是客户端声明，不可信**。只按它校验文件类型等于开放任意文件上传，必须读文件头魔数（JPEG `\xff\xd8\xff` / PNG `\x89PNG` / WebP `RIFF..WEBP`）验证真实格式。
12. **文件名可枚举 = 隐私泄露**。学信网截图含真实姓名学号，`verify_{user_id}_{时间戳}.jpg` 可被批量拼接下载。文件名必须加随机串（`secrets.token_hex`），敏感文件更应走鉴权下载而非公开静态目录。
13. **上传逻辑收敛**：多个上传接口各自复制粘贴「类型校验+大小校验+落盘」是坏味道，收敛到一个 `upload_service.save_upload_image` 后，修一个 bug 就能覆盖全部入口。

### 前端（微信小程序）

14. **`es6: false` 关闭 Babel 转译**时，基础库 3.x 原生支持 `async/await`，不需要 regeneratorRuntime；开 `es6: true` 反而要装 babel runtime 依赖。
15. **WXML 标签必须配对**，`<view>` 开头用 `</view>` 结尾，混用会导致整页不渲染。
16. **`wx.switchTab` 只能跳 tabBar 页面**；非 tabBar 页面用 `navigateTo`/`reLaunch`。
17. **button 有微信默认样式**，纯展示按钮用 `<view>` 代替。
18. **`wx.uploadFile` 与 `wx.request` 是两套 API**，上传要自己带 token、自己解析错误；两边的 401 处理行为要统一（本项目统一为「清 token + 不强制跳转」）。
19. **移除 tabBar 后清理残留**：`wx.showTabBarRedDot` 之类调用会静默失败，重构时全局搜一遍。
20. **字符串索引不可靠**：WXML 里 `name[0]` 取队名首字符不可靠，应在 JS 里算好字段（`logo_initial`）再交给模板。

### AI 审核

21. **AI 结果必须分级使用**：置信度 ≥0.9 才自动通过/驳回，否则转人工——既省人力又不放跑错误；AI 调用异常一律降级为人工审核，不阻断上传主流程。
22. **AI 输出要归一化**：模型可能返回 `S0`/`s10`/`C +` 等变体，`normalize_rank` 统一成合法段位；管理员手动输入同样走归一化，非法值直接 400，保证库内数据干净。

## 📝 教训与反思

1. **一个拼写错误让整条审核链断裂了很久**：`/registerations/.../approve`（应为 registrations）加上前端没有调用方法，导致队伍报名永远 pending、自动编排静默跳过报名队伍——直到安全审查才暴露。教训：**关键业务路径要端到端走一遍**，且路由名/字段名这类字符串错误不会被编译器发现。
2. **前端拦截不是安全边界**：报名状态校验前端有、后端没有，直接调 API 就能在 finished 赛事报名。任何安全/业务规则都必须后端兜底，前端拦截只是体验优化。
3. **权限模型要一开始就分层**：reviewer 最初被 `require_admin` 等同于 admin，后期想收缩为最小权限要改十几个路由 + 前端显隐，成本翻倍。权限设计宜「先严后松」。
4. **公共函数要尽早抽**：队长鉴权（404+403）、入队人数上限、上传落盘，都是在重复出现两三处之后才抽的。第二次出现同类代码时就应该抽函数。
5. **SQLite 的便利掩盖了生产风险**：外键、唯一约束、并发行为都与 MySQL 有差异，关键路径必须在生产形态（MySQL）验证一次。
6. **安全审查要主动、多角度**：这次从「权限越权/报名业务/队伍业务/上传安全/并发一致性/前端体验」六个角度系统 review，才把积累的 27 个问题一次性挖出来。写代码时多想一步「如果我是攻击者/恶意用户，能怎么滥用这个接口」。

### 数据库迁移记录（已执行；新环境部署时需重放）

> SQLAlchemy `create_all` 只建新表，不补列/不补约束。以下三条是项目演进中积累的迁移 SQL，**线上与本地库均已执行**；在新的数据库环境从零部署时需要重新执行。

本地（`D:\mysql` 的 `cs2_competition` 库）与生产（docker compose 的 mysql 容器）各执行一次：

```sql
-- ① 时间协商：对阵双方确认状态
ALTER TABLE match_rounds
  ADD COLUMN team1_confirmed TINYINT(1) DEFAULT 0 COMMENT '队伍1是否已确认比赛时间',
  ADD COLUMN team2_confirmed TINYINT(1) DEFAULT 0 COMMENT '队伍2是否已确认比赛时间';

-- ② 队伍自定义 Logo
ALTER TABLE teams ADD COLUMN logo VARCHAR(255) NULL COMMENT '队伍Logo图片路径';

-- ③ 报名防重唯一约束（执行前先查重清理：
--    SELECT match_id, user_id, COUNT(*) FROM registrations
--    GROUP BY match_id, user_id HAVING COUNT(*) > 1;）
ALTER TABLE registrations ADD CONSTRAINT uq_registration_match_user UNIQUE (match_id, user_id);
```

`stage_windows` 为新表，后端启动时 `create_all` 会自动创建。
