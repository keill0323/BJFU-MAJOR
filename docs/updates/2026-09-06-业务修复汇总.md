## 2. 九项主要问题与修复结果

| # | 原问题与触发场景 | 修复后的行为 |
| --- | --- | --- |
| 1 | 两个账号使用同一学号凭证，第二个账号虽未写入学号，仍被自动认证通过 | 自动通过要求有效且未被其他账号占用的学号；缺失、格式异常或冲突转人工，数据库唯一约束冲突也有兜底 |
| 2 | 生成淘汰赛时只计算晋级三队之间的成绩，导致原小组第一被换成第二名轮空 | 排名保留晋级队伍对未晋级队伍的全部该阶段成绩，轮空名额与完整小组排名一致 |
| 3 | 小组赛一场未打也能晋级；附加赛仅完成一场即可结束 | 检查循环赛对阵是否完整生成、所有场次是否结束，全部满足后才能晋级；先完成所有组的校验再修改进度 |
| 4 | 淘汰赛期间还能重分种子，清空分组却保留旧对阵 | 已生成对阵或已完成后续阶段晋级时，禁止重新分配种子和分组 |

| 6 | 个人报名后建队没有整队报名入口；通过接口升级后，个人 `approved` 掩盖队员 `pending`，后台没有审批按钮也没有赛事进度 | 队长可以从页面把个人报名升级为整队报名；整队记录统一待审，审批重新校验阵容并建立 `TeamProgress`；后台按全队状态显示审核入口 |
| 7 | 玩家被踢后，重放之前已接受的邀请便能自行重新入队 | 只有 `pending` 邀请或申请可以被处理；已接受或已拒绝的记录不能再次用于入队，新邀请仍可正常接受 |

| 9 | 半决赛生成后更正四分之一决赛胜者，半决赛仍保留原胜者 | 比分用于后续晋级后禁止直接修改；下一阶段尚未生成时仍可更正当前阶段比分，无组别手动对阵也可正常录分和更正 |

## 3. 补充修复

### 3.1 认证与 AI 审核

- **重传材料开启新的审核状态**：清除上一张截图的 AI 结论、置信度和人工驳回原因，新截图进入 `pending`。
- **校验 AI 输出**：检查结果是否为对象、置信度是否为 0–1 的有限数值，以及结论、学号、段位和理由的字段类型。异常返回转人工，不因字符串置信度或 `null` 等输入导致接口 500。
- **迟到结果保护**：AI 返回后重新检查当前截图与审核状态，旧截图的结果不会覆盖新截图或已完成的人工审核。
- **首次段位人工审核接通**：AI 关闭、失败或置信度不足时，保存截图并创建现有 `RankApplication` 待审记录；管理员可通过已有段位申请界面查看证据。
- **防止无效审批和重复申请**：同一用户已有待审申请时不能重复提交；AI 没有识别出有效段位时，管理员必须指定有效段位才能批准。

自动学籍认证目前接受 **6–20 位 ASCII 数字学号**；不符合该格式的材料转人工核验。这是自动审核条件，不替代学校实际学号规则的人工确认。

### 3.2 小程序页面

- 队长先个人报名、再建队后，仍可看到并提交“队伍报名”；成功升级为随队报名后关闭该入口。
- 阶段时间窗口直接通过 `getStageWindows()` 读取，不再依赖已生成的对阵；尚无对阵也能查看、编辑已保存时段。
- 时间窗口读取失败明确提示错误，避免将读取失败误显示为“尚未设置”。
- 报名流程中的“去认证”跳转独立认证页。
- 首次段位认证与后续段位更新使用兼容两种场景的审核提示，并引导用户到消息页查看结果。

### 3.3 一致性与兼容性

- 队伍成员、报名和评分同步失败时整体回滚，不留下只完成一部分的记录。
- 对阵生成采用一次事务；中途失败时不会提交半份赛程。
- 未认证用户退队时，各赛事保留各自原有报名状态，避免拿任意一条记录覆盖其他赛事状态。
- 已结束的新生赛不再因历史报名阻止正常退队；未报名队伍的一般组队流程继续保留。
- 旧数据中“报名全为 `approved`，但缺少赛事进度”的队伍会显示为待审核，管理员可重新审批补齐。

## 4. 关键实现

### 报名审核

个人报名通过与队伍参赛通过是两个不同状态。个人记录升级为随队记录时统一设为 `pending`，队伍审批重新核验：

1. 队伍自身已通过审核。
2. 当前成员完成学籍和段位认证。
3. 人数未超上限，新生赛至少有 3 名新生。
4. 当前成员与随队报名记录一致。

校验通过后，在同一事务内更新报名状态并建立赛事进度。调用单条随队报名审批入口时，也会执行整队审批，避免只放行一人就进入编排。

### 数据库锁与事务

新增 `services/locking.py` 中的 `lock_row(db, model, row_id)`：

- MySQL 使用 `SELECT ... FOR UPDATE` 锁定记录。
- SQLite 先执行不改变主键值的 `UPDATE` 获取数据库写锁，再读取记录，避免 SQLite 忽略 `FOR UPDATE`。
- 锁保持到调用方提交或回滚。成员人数和报名状态等关键读取使用当前读，减少 MySQL 默认隔离级别下旧快照造成的判断偏差。

`recalc_team_rating()`、`sync_member_registrations()` 等内部操作支持 `commit=False`，供业务入口组织一次完整事务。赛事编排和晋级操作也先锁赛事记录。

### 晋级与比分

排名继续按“胜场 → 净胜分 → 队伍评分”计算，修复的是候选队伍缩小时被遗漏的比赛成绩。赛制仍为现有的挑战者小组、附加赛、8 队传奇组和 6 强淘汰赛。

本次采用**晋级后锁定前序比分**的处理方式，没有增加自动回退赛程或重建后续对阵的功能。已发生的历史错误晋级需要管理员核对，不能通过直接改前序比分完成修复。
