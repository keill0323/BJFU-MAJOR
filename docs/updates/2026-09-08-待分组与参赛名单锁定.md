# 2026-09-08 待分组与参赛名单锁定

本轮修复报名审核与赛事编排之间的状态混淆：队伍通过报名后显示「待分组」；开始编排后锁定参赛队伍名单，不能继续加入新队伍。代码已完成本地验证，尚未部署，无新增数据库迁移。

## 通过报名后显示待分组

此前通过报名会建立默认阶段为 `challenger` 的赛事进度，页面因此立即显示「挑战者组」，容易让管理员误以为队伍已完成分组。

现在使用报名状态与编排信息共同判断：`registration_status` 为 `approved`、阶段为 `challenger`、种子尚未分配（`seed` 为 0 或空值）、`group_name` 为空时，显示「待分组」。待审核、已驳回的报名不会被当作待分组队伍。

- 管理端赛事详情新增待分组队伍区，可直接进入「分配种子并分组」。
- 用户端与管理端的队伍状态、排名标签统一显示「待分组」，这些队伍不计入实际挑战者队伍列表或分组。
- 完成编排后，前 4 支种子队伍显示传奇组，其余队伍按实际挑战者小组显示。

沿用已有赛事进度字段，没有新增 `waiting` 数据库阶段；现有已通过但尚未编排的队伍重新加载页面即可得到正确标签。

## 编排后锁定参赛队伍名单

后端依据真实编排记录判断名单是否锁定。任意一项成立即锁定：

- 已有正整数种子编号。
- 已有非空小组名称。
- 已有传奇组、淘汰赛或已淘汰阶段的队伍。
- 已生成任何对阵。

赛事详情返回 `roster_locked`。前端读取该字段，并兼容根据种子、组别、阶段和对阵判断锁定状态；把赛事状态改回「报名中」也不会绕过已有编排记录。

锁定后，管理端显示「已分组，参赛名单已锁定」，隐藏新报名的通过按钮。审批事件在打开确认框前、确认提交时均检查名单状态；后端仍在赛事行锁内校验，防止两个管理员同时分组与审批时加入遗漏队伍。

| 入口或操作 | 锁定后的处理 |
| --- | --- |
| 新队伍报名，包括个人报名转为新队伍报名 | 拒绝新增参赛队伍 |
| 整队报名审批、旧版逐条报名审批 | 均不能批准新的参赛队伍 |
| 已批准报名但缺少赛事进度的旧数据补齐 | 不能在编排后补建新参赛队伍 |
| 混合已通过与待审记录的再次审批 | 拒绝把未完成审批的队伍加入编排 |
| 入队后自动补报名 | 无既有赛事进度的队伍不能借此绕过名单限制 |
| 已有赛事进度且全部报名已通过的重复审批 | 返回已有结果，不改变种子、组别或比赛阶段 |

这里锁定的是赛事的参赛队伍集合。自由人个人报名及既有参赛队伍按原规则补充成员仍使用各自的认证、人数、报名时间等校验，不会因本次修复一律关闭。

## 种子与分组一次提交

旧页面先请求「分配种子」，再请求「分组」。第二步若因人数不足失败，第一步已保存的种子会使名单提前锁定，管理员无法继续审核足够队伍。

新增 `POST /api/matches/{match_id}/seed-and-group`，使用 `group_names` 查询参数提交小组名称。管理端分组操作改为仅调用该接口：在同一个赛事锁和数据库事务内验证组别、检查人数、按队伍水平分分配种子、蛇形分组；任何异常都会回滚，不留下半份编排。

- 继续支持三组与四组。每个挑战者小组至少 2 支队伍，另有 4 支直升队伍。
- 三组保留附加赛，四组的小组冠军直接晋级且不设附加赛。
- 前端阻止重复提交；分组失败保留待分组数据并显示错误，允许重试。
- 分组成功立即关闭新审批入口，再刷新队伍；刷新失败也不会重新开放已锁定的审批入口。
- 已生成对阵或完成后续阶段晋级时，仍不能重新分配种子或分组。
