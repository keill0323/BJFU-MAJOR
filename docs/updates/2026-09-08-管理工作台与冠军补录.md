# 2026-09-08 管理工作台、待办提醒与冠军补录

本轮完成代码，后端与小程序由项目维护者部署。未连接服务器、修改线上数据库或上传小程序。此前的部署压缩包不含本次功能，发布时需同步当前代码。

## 管理界面

- 默认进入「待办总览」，以四个待办卡片展示在校认证、段位审核、队伍审核和赛事报名，点击可进入对应列表。
- 六个管理栏目采用两行布局；数字角标、错误与空状态分开显示。申请处理后刷新计数，读取失败保留上次数字并标明待更新，不显示虚假的「没有待办」。
- 赛事报名按队伍计数，不把一支队伍的多名成员算成多条队伍待办；按赛事提供入口，并标明已分组的遗留报名。名单锁定仍按原业务规则执行，不因待办入口放开审批。
- 修复原管理页调用公开队伍接口的问题，改用 `/api/teams/admin`，展示待审核及已驳回队伍，待审核队伍排在前面。
- 赛事列表优先展示，创建表单默认收起，展开后定位到表单；字段增加清楚的标签。保留报名时间、审批、用户资料与赛程管理操作。
- 冠军补录与修改账号权限仅管理员可操作；审核员可处理认证、段位、队伍和赛事待办。

## 更明显的待办提醒

管理员或审核员在首页、个人中心、消息页可看到带数量的「管理待办」提示，点击进入管理工作台。侧边栏管理入口显示数字角标，菜单图标显示红点；普通用户不请求或显示管理摘要。

摘要使用独立轻量接口，仅查询计数及待审赛事名称，不为提示数字下载所有用户资料、认证截图或完整队伍列表。后端固定使用两条只读聚合查询；前端按需加载当前管理栏目。

同一登录账号的多个入口合并在途摘要请求，使用 30 秒内存缓存。进入管理页、返回管理页、下拉刷新和审核完成时更新；赛事详情中审批或分组成功会使缓存失效。退出或切换账号清除摘要，迟到请求不能恢复旧角标。没有添加后台轮询或微信订阅消息推送。

## 冠军补录操作

操作路径：**管理工作台 → 赛事管理 → 已结束赛事 → 补录冠军**。总览中的「冠军补录」也会引导到赛事列表。

1. 选择已结束的赛事。平台没有记录的往届比赛，需要先在赛事管理创建对应赛事，并设置为已结束。
2. 填写历史冠军队名和夺冠日期；可从现有战队带入队名与阵容，也可以手动填写已解散的队伍。
3. 核对夺冠时阵容，每行填写一名选手。现有队伍的成员是当前资料，需要人工确认是否符合历史记录。未知阵容可留空。
4. 亚军与比分选填；比分须同时填写或同时留空，冠军比分必须大于亚军。不会用假比分或假账号 ID 填充缺失记录。
5. 填写补录依据或来源，在确认弹窗中核对赛事、队伍、日期和阵容后保存。保存成功即进入名人堂，并标记「管理员补录」。

已有人工补录可再次打开修改，保存携带版本号，避免覆盖其他管理员的更新。可以解除战队和选手账号关联，保留历史文字、段位与图片资料，支持队伍或账号删除后继续维护档案。

已有正式赛程生成的冠军保持只读，需要通过决赛比分修正；存在完整有效决赛但尚未归档的旧赛事仍走原来的 `backfill_champions` 历史归档流程。人工补录独立保存历史阵容，不随当前队伍变化或后续比分编辑而改写。原赛事删除后，荣誉仍保留。

补录者、最后修改者、补录时间、备注与版本仅用于管理记录；公开名人堂响应不暴露这些私有字段。

## 接口

| 接口 | 权限与作用 |
| --- | --- |
| `GET /api/admin/todos` | 管理员/审核员；四类待办计数、分赛事报名数量及锁定状态 |
| `GET /api/hall/admin/champions/{match_id}` | 仅管理员；读取冠军及管理备注、版本 |
| `PUT /api/hall/admin/champions/{match_id}` | 仅管理员；新增或编辑人工冠军档案 |

冠军管理接口返回 `{champion, note, updated_at, version}`，保存时携带 `expected_version`。冲突返回 409，表单保留输入；重新打开档案核对后再提交。不存在的新后端接口仍显示版本升级提示，不尝试不安全的旧写入接口。

## 数据库升级与部署

需要数据库迁移。`champion_snapshots` 的决赛对阵、关联队伍、亚军和比分允许为空，新增人工录入者、更新者、时间、备注与版本列。`Base.metadata.create_all()` 不会替已有表修改列，因此必须执行显式迁移。

迁移脚本为 `backend/app/migrations/manual_champions.py`，支持现有项目的 MySQL/MariaDB 和 SQLite；不存在冠军表时创建，已完成升级时跳过。保留现有冠军数据。MySQL 的 DDL 不具备整段事务回滚能力，脚本可重复执行，但发布前仍需备份并停止 API 写入。

在服务器上传当前代码、保留服务器原 `.env` 后，于包含 `docker-compose.yml` 的项目目录执行（现有服务器目录为 `/home/ubuntu/app`）：

```bash
cd /home/ubuntu/app
set -e
umask 077

# 先构建新镜像，减少停机等待；数据库服务保持运行。
docker compose build backend
docker compose stop backend

# 密码从数据库容器自身环境读取，不需要写入命令或聊天。
docker compose exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" exec mysqldump -uroot --single-transaction --routines --triggers cs2_competition' > "before-manual-champions-$(date +%Y%m%d-%H%M%S).sql"

# 使用新镜像执行迁移，成功后才启动新 API。
docker compose run --rm --no-deps backend python -m app.migrations.manual_champions
docker compose up -d --no-deps backend
docker compose restart nginx
docker compose logs --tail=80 backend
```

如果迁移失败，不要跳过失败继续启动新 API；检查错误后重复运行迁移。数据库和上传目录的持久化卷继续保留。迁移后再上传对应小程序代码；仅更新前端会使待办/补录入口提示服务器不支持或无法加载。

非 Docker 环境：在实际服务虚拟环境中、以 `backend` 为工作目录执行 `python -m app.migrations.manual_champions`，成功后重启 API 服务。
